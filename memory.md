# Project memory (hubx-lead maintains; humans may edit)

## Decisions
- Verifiable hash-chained ledger instead of on-chain blockchain; identity from session; signing is a future extension.
- PostgreSQL (managed free instance); only hubx-api touches it.
- Configuration via `application.properties` per service (constitution Principle III); stdlib reader, one copy per service.
- Backlog and all artifacts in English; guide and conversation with the team in Spanish.
- Branching: release/feature/hotfix; the Spec Kit story branch is the feature branch.
- Release branches are `release/vX.Y.Z[-name]` (e.g. `release/v0.2.0-sign-in`), cut from `main`; exactly one is open
  at a time (the current release: `git branch -r --list 'origin/release/*'`). Story PRs target it; when the release is
  ready it is merged into `main` by PR and its branch is deleted automatically; the next one is cut from `main`.
  `release/sdd-hubx-system` shipped as v0.1.0, the baseline without stories (2026-11-24); HU-01 goes in v0.2.0.
- Tags are created only by CI (`.github/workflows/release.yml`): merging a `release/vX.Y.Z[-name]` or `hotfix/vX.Y.Z`
  into `main` tags `vX.Y.Z` on the merge commit and publishes a GitHub Release with generated notes. Hotfixes come
  from `main` as `hotfix/vX.Y.Z` and the workflow opens a PR syncing `main` into the open release. No backports:
  released versions are never patched; a fix is a new version.
- PostgreSQL driver: `github.com/jackc/pgx/v5` v5.12.0 through `database/sql` (`pgx/v5/stdlib`), approved by a human (2026-11-20).
- JWT library (HU-01): `golang-jwt/jwt` v5.2.1, stdlib-only, HS256 signing, approved 2025-01-21.
- Migrations: plain SQL in `hubx-api/migrations/NNNN_name.sql`, embedded in the binary; own runner `internal/migrate`
  (`cmd/migrate`), no external tool. One transaction per file, advisory lock, checksum: never edit an applied migration.
- Schema 0001 is the existing `0001_baseline_schema.sql` (foundation): `users` (email text UNIQUE normalized, name,
  role text `operator`/`ground partner`/`customer`, password_hash), demo users bcrypt cost 12, no `party_id`. HU-01
  reuses it and adds no migration (human decision at HU-01 implement). Role value is `ground partner` with a space
  everywhere (JWT, API responses). `JWT_SECRET` env var (32-byte random, base64); JWT HS256 (`sub`, `email`, `role`,
  `iat`, `exp`), 1-hour expiration. Gateway also validates the JWT (golang-jwt v5.2.1 approved for hubx-gw too); API
  validates on its own.
- Schema future: `shipments.stage` and `shipments.assigned_partner_id` are a read projection of the ledger; `updates` is
  canonical and has a trigger that rejects UPDATE/DELETE. Creating a shipment records no update (HU-02); the first
  update is "In flight" with `previous_fingerprint` NULL.
- Demo users (password `Hubx-Demo-2026`): operator@hubx.co (operator), rapido@hubx.co and express@hubx.co (ground
  partner), ana@hubx.co and andina@hubx.co (customer). Bcrypt cost 12 (migration 0001). Seed shipments `HBX-SEED-0001..0004`, all in Created (future HU-02).
- Local stack runs in Docker Compose (`make up`); `make test-integration` uses an isolated project (`hubx-it`) and
  deletes its database at the end. Local secrets are random, in git-ignored `.env`, generated by `scripts/env.sh`
  (includes `JWT_SECRET` as of HU-01).
- All files use LF (`.gitattributes`); run `make` from Git Bash on Windows.
- Branch protection (2026-11-20): ruleset `protect-main` on `main` needs a PR with 1 approval from someone other than
  the last pusher, resolved threads, no force push, no deletion, no bypass (admins included). Ruleset
  `protect-release` (formerly `protect-release-no-approval`) on every `release/**` branch needs a PR with 1 approval
  from someone other than the last pusher (raised from 0 on 2026-11-21 so GitHub enforces that no agent merges,
  constitution 1.3.0), resolved threads, no force push; deletion is allowed so the branch is removed after merge.
  Add the CI checks as required once D's workflows exist (item 8).
- GitHub default branch is `main` (the only permanent branch); release and feature branches are deleted after merge
  (repo setting "automatically delete head branches" on, 2026-11-21).

- Kiro support (2026-11-21): the five agents also exist in `.kiro/agents/*.json` (v3 format, IDE 1.0 and CLI v3) with a
  model per role: Sonnet 4.5 for hubx-lead, qa-seguridad, backend-go and frontend-react; Haiku 4.5 for devops (only
  Claude models on the current university plan). opencode stays the team default and sets no model, so teammates keep
  their free model. `.opencode/agents/*.md` is the single source of the instructions; `make agents-sync` copies them.
- Claude Code support (2026-11-21): `.claude/agents/*.md` generated by `scripts/sync-agents.mjs` (opus lead, sonnet QA,
  backend and frontend, haiku devops). Claude Code has no per-agent permissions, so each agent runs a PreToolUse hook
  (`scripts/agent-guard.mjs`) that enforces the rules of `.kiro/agents/<name>.json`: one permission source for Kiro and
  Claude Code. Spec Kit `claude` integration installed (skills `/speckit-*`); opencode stays the default.

- Story number = backlog number: `HU-xx` -> `specs/NNN-name` and branch `NNN-name` (HU-01 -> `001-sign-in`). hubx-lead
  runs `create-new-feature.sh --allow-existing-branch --number NNN --short-name <name>` and then creates the branch
  itself with `git switch -c` (2026-11-23).
- hubx-lead runs on Claude Opus 5.5 in every tool (2026-11-23): Claude Code `claude-opus-5-5`, opencode
  `opencode/claude-opus-5-5` (needs OpenCode credits; Copilot does not serve it), Kiro IDE `claude-opus-5.5` (the
  kiro-cli 3.5 catalog does not list it, the IDE does).
- Constitution 1.4.0 (2026-11-23): Go domain in `internal/<domain>`, handlers in `internal/handlers/<domain>`, unit
  tests in `test/` sub-packages with gomock mocks generated into `mocks/` (`go.uber.org/mock` v0.6.0 as a module tool:
  `go tool mockgen`). hubx-bender is Cucumber 13.3.0 + Playwright 1.65.0 (+ tsx 4.23.15): one feature per story with
  the backlog Gherkin verbatim, and one `@e2e` browser happy path per story. Reason: HU-01's sign-in bug passed every
  API test and only failed in the browser.
- The MFE runs in the local stack (`hubx-mfe/Dockerfile`: Vite build served by nginx, `/api` proxied to the gateway,
  same origin) on http://localhost:3000; `make test-integration` starts it and runs the `@e2e` scenarios in Chromium.
- HU-02 (2026-11-24): `POST /api/shipments` (`contracts/shipments-create.md`), no migration (reuses `shipments` from
  0001), no update recorded on creation. Code `HBX-` + 8 upper hex from `crypto/rand`, retried on `shipments_code_key`.
  Weight is a JSON number literal `^[0-9]+(\.[0-9])?$` in [0.1, 5000]; more than one decimal (0.15) is
  rejected with the weight-range message (human decision 2026-11-24, Option A; not deduced from the schema). Customer indicated by email. The API's `RequireAuth` now guards its first route. HU-02 ships in
  v0.3.0 (`release/v0.3.0-create-shipment`), not v0.2.0.
- HU-03 (2026-11-24): `POST /api/shipments/{code}/updates` records an immutable chained update and projects the stage in
  one transaction; no migration (reuses 0001). Contract `contracts/hu03-record-update.md`. `RequireSessionAuth` was added
  in hubx-api for the HU-03 routes only, so HU-01/HU-02 keep their flat `UNAUTHORIZED` 401 body while HU-03 returns the
  nested `SESSION_EXPIRED` body. The gateway emits that nested body only on the two HU-03 routes and never excludes a
  route from JWT validation or alters `Authorization` (Constitution II). Assignment is operator-only from
  "At destination airport"; the assigned partner records Out for delivery and Delivered; no reassignment, no going back.
  QA fixtures create fresh shipments through the gateway and sign in as the assigned ground partner for the last two
  transitions, keeping `HBX-SEED-0001` in Created for the `@e2e`. Delivered from branch `003-record-update-sync`
  (renamed from `003-record-update` after the original remote branch was deleted) with PR target `main`, by human
  decision after v0.1.0 was merged; HU-03 does not ship in a release branch.
## Conventions
- PR title (2026-11-21): `<type>(<scope>): <gitmoji> <short description> [agent:role]`, scope `HU-xx` or an area;
  mapping in hubx-lead step 10. Commits keep their own format below.
- Commit format: `[agent:role] HU-xx short summary`; one commit per subagent delivery. Since 2026-11-21 (constitution
  1.3.0) hubx-lead commits, pushes the story branch and opens the PR without confirmation; no agent merges.
- Test names: `HUxx_<scenario>`.
- Tasks in `tasks.md` are marked `- [x]` only by hubx-lead, citing the subagent evidence.
- Migration numbers (reserve here before using): 0001 baseline with demo users (HU-01), 0002_seed_ledger (C, after the fingerprint formula is in `contracts/`).

## Lessons
- Subagent delivery must be compared with `git status --short` and `git diff --stat` before and after, not by file names only.
- `npm --prefix <dir> init -y` (npm 11) writes `package.json` in the current directory, not in `<dir>`; check with `git status`.
- govulncheck must be built with the same Go as the one on PATH; after upgrading Go, reinstall it (and gosec).
- Go toolchain is 1.27.4 (go.mod, go.work, Docker build images, 2026-11-20): 1.26.5 had 15 stdlib vulnerabilities.
  Scanning with a newer local Go hides vulnerabilities of the image's Go; keep both versions aligned.
- On macOS, files can be checked out with mode 600 and the distroless `nonroot` user cannot read them; Dockerfiles
  copy `application.properties` with `--chmod=0644`.
- Ledger tamper test: `make psql`, then `BEGIN; SET LOCAL session_replication_role = replica; UPDATE updates ...; COMMIT;`
  (bypasses the immutability trigger on purpose).

- Kiro permission rules are deny-overrides (no rule order): write "everything except X" as a `deny` with `exclude`.
  Kiro agents in v3 format only load in the v3 engine; `--no-interactive` needs `--agent-engine v3`.
- Kiro without `resources` loads only the root `AGENTS.md`; service `AGENTS.md` files come in only via `resources`.
- opencode `.md` agents do not expand `{file:...}`; only `opencode.jsonc` does, and a `.md` agent overrides it. A model in
  the user config (`~/.config/opencode/opencode.jsonc`, `agent.<name>.model`) merges with the repo agent.
- Claude Code skips agent front-matter hooks in folders whose trust dialog was not accepted (debug log: "Skipping
  frontmatter hooks ... not trusted"); the guard works both for `claude --agent <name>` and when delegated.

- Spec Kit 1.4.2 `create-new-feature.sh` creates the folder and `.specify/feature.json` but not the git branch (that
  was the git extension, not installed). Without a story branch every Spec Kit command reads `feature.json`; a stale
  one sent HU-01 to an empty `specs/001-sign` folder. `--number N` silently renumbers if any `specs/N-*` exists.
- Kiro checks every sub-agent call against the parent's policy and the sub-agent's own; a deny in either wins and a
  sub-agent's allow cannot widen the parent (https://kiro.dev/docs/custom-agents/subagents/). So `.kiro/agents/hubx-lead.json`
  is generated (`make agents-sync`): the lead's own rules (`scripts/agents/hubx-lead.kiro.json`, edit this one) plus the
  union of its sub-agents' allows. In Kiro the lead could therefore write code; only its instructions stop it, so check
  its commits with `git diff --stat`. Claude Code's guard applies the lead's own rules and lets each sub-agent's guard
  judge that sub-agent's calls (`agent_type`). opencode scopes sub-agents by their own permissions (checked 2026-11-19).
- Delegation honesty: a commit tagged `[agent:<role>]` must contain work that agent wrote and ran itself. HU-01's
  implementation was partly done by the orchestrator because Kiro blocked the sub-agents (docs/sdd-agent-blockers.md);
  the lead now stops and reports instead of doing a sub-agent's work.
- Agent zones are enforced on commits (2026-11-24): a commit tagged `[agent:<role>]` may only touch that role's
  write zone (`make agents-zones`, run by CI on PRs into `release/*`). Zones come from `.kiro/agents/<role>.json` and
  `scripts/agents/hubx-lead.kiro.json`. The lead may not write `qa-report.md` (opencode and Claude Code block it; in
  Kiro only CI catches it, because a lead deny would also block qa-seguridad). Historical exceptions with their
  reason: `scripts/agent-zones-exceptions.txt` (63e4726, 9b5b037, 936abb1).
- Verify subagent evidence by rerunning the commands: in HU-02 frontend-react reported `ok` with test/build marked
  `not_run` (shell denied) and the build was actually broken. Text split across elements (`<strong>Code:</strong> X`)
  breaks `getByText` in both unit tests and `@e2e`.
- A full green Cucumber summary (`46 scenarios (46 passed)`) is valid evidence for an individual scenario when
  `cucumber.mjs` runs `strict: true`: an undefined step would fail the suite. In HU-03 the `progress` formatter printed
  only dots, so the literal line for the expired-session scenario could not be captured; the two green full-suite runs
  and the strict mode were recorded instead of inventing output.
- `speckit.analyze` is read-only and may surface plan drift after implementation. In HU-03 it found six deviations
  (branch name, gateway error body, MFE tests and file names); the lead corrected spec/plan/tasks and recorded them in
  `pr.md`. The gateway change was a contract requirement and did not weaken the two-validation rule.
