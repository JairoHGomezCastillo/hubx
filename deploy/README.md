# Render Deployment

Free-tier deployment of hubx to Render (services) + Neon (PostgreSQL).

## Setup Steps

### 1. Create Neon PostgreSQL Project

1. Go to https://console.neon.tech
2. Create a new project (auto-generated credentials)
3. Copy the **DIRECT** connection string (not pooled):
   ```
   postgresql://user:password@ep-xxx.us-east-1.neon.tech/hubx?sslmode=require
   ```
   - Use the direct URL, not the pooled one (`pooler` in the hostname)
   - Direct URL is required for the migration runner's advisory lock

### 2. Create Render Blueprint

1. Go to https://dashboard.render.com/blueprints
2. Click "New Blueprint" and select your GitHub repository
3. Set **Blueprint path**: `deploy/render.yaml`
4. Set **Branch**: `main` (or the current release branch)
5. Create the blueprint (Render will parse the services and environment groups)

### 3. Run Migrations

Migrations **must** run once before the API starts. Because Render's free tier has no pre-deploy hooks, run this from your laptop:

```bash
DB_URL="postgresql://user:password@ep-xxx.us-east-1.neon.tech/hubx?sslmode=require" \
  go -C hubx-api run ./cmd/migrate
```

**Why DIRECT URL here?**
- The migration runner uses PostgreSQL advisory locks (`pg_advisory_xact_lock`) to ensure only one instance runs at a time
- Advisory locks do not work through the connection pooler (Neon's pooled endpoint returns a connection per request, breaking lock state)
- The direct endpoint bypasses the pooler and allows the lock to function
- The API's `DB_URL` also uses this DIRECT URL (the Blueprint does not configure a pooled connection)

### 4. Set Environment Variables in Render

After creating the blueprint, Render will prompt you to fill in environment variables marked `sync: false`:

#### Generated (by Render, do not edit):
- `JWT_SECRET` — 32-byte random, base64, auto-generated by Render
- `GATEWAY_SECRET` — shared secret for API-gateway trust, auto-generated by Render

#### Manual (paste from above):
- `DB_URL` — the DIRECT Neon connection string from step 1 (not pooled)
- `API_URL` — public HTTPS URL of hubx-api (e.g., `https://hubx-api.onrender.com`), set after first deploy
- `GATEWAY_URL` — public HTTPS URL of hubx-gw (e.g., `https://hubx-gw.onrender.com`), set after first deploy

**Note on `sync: false`:**
These variables are not auto-synced because the Blueprint reference has no way to express public HTTPS service URLs. After the first deploy, Render will assign public URLs; copy them into `API_URL` and `GATEWAY_URL` manually, then trigger a redeployment.

### 5. First Deploy

1. Click "Deploy Blueprint" in the Render dashboard
2. Wait for all three services to build and start
3. Copy the public `.onrender.com` URLs assigned to `hubx-gw` and `hubx-api`
4. Update `API_URL` (gateway → api) and `GATEWAY_URL` (mfe → gateway) in the Render environment
5. Trigger a redeployment of hubx-gw and hubx-mfe

### 6. Verify Deployment

After services restart:

```bash
# Gateway health (public, no auth required)
curl -s https://<hubx-gw-url>.onrender.com/health | jq .

# API health through the gateway (public, no auth required)
curl -s https://<hubx-gw-url>.onrender.com/api/health | jq .
```

## Notes on Free Tier

- **Render free services** sleep after a period of no traffic and cold-start on the next request (expect a slow first response).
- **Neon free Postgres** suspends (scale-to-zero) after inactivity and resumes on the next connection; the first query after a suspend is slow.
- Because of these two, the very first request after idle can take tens of seconds. Retry if it times out.
