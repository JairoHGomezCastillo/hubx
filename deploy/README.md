# Render Deployment

Free-tier deployment of hubx to Render (services) + Neon (PostgreSQL).

## Setup Steps

### 1. Create Neon PostgreSQL Project

1. Go to https://console.neon.tech
2. Create a new project (auto-generated credentials)
3. Copy the **DIRECT** connection string (not pooled):
   ```
   postgresql://user:password@ep-xxx.us-east-1.neon.tech/hubx?sslmode=require
   ```
   - Use the direct URL, not the pooled one (`pooler` in the hostname)
   - Direct URL is required for the migration runner's advisory lock

### 2. Create Render Blueprint

1. Go to https://dashboard.render.com/blueprints
2. Click "New Blueprint" and select your GitHub repository
3. Set **Blueprint path**: `deploy/render.yaml`
4. Set **Branch**: `main` (or the current release branch)
5. Create the blueprint (Render will parse the services and environment groups)

### 3. Run Migrations

Migrations **must** run once before the API starts. Because Render's free tier has no pre-deploy hooks, run this from your laptop:

```bash
DB_URL="postgresql://user:password@ep-xxx.us-east-1.neon.tech/hubx?sslmode=require" \
  go -C hubx-api run ./cmd/migrate
```

**Why DIRECT URL here?**
- The migration runner uses PostgreSQL advisory locks (`pg_advisory_xact_lock`) to ensure only one instance runs at a time
- Advisory locks do not work through the connection pooler (Neon's pooled endpoint returns a connection per request, breaking lock state)
- The direct endpoint bypasses the pooler and allows the lock to function
- The API's `DB_URL` also uses this DIRECT URL (the Blueprint does not configure a pooled connection)

### 4. Set Environment Variables in Render

After creating the blueprint, Render will prompt you to fill in environment variables marked `sync: false`:

#### Generated (by Render, do not edit):
- `JWT_SECRET` — 32-byte random, base64, auto-generated by Render
- `GATEWAY_SECRET` — shared secret for API-gateway trust, auto-generated by Render

#### Manual (paste from above):
- `DB_URL` — the DIRECT Neon connection string from step 1 (not pooled)
- `API_URL` — public HTTPS URL of hubx-api (e.g., `https://hubx-api.onrender.com`), set after first deploy
- `GATEWAY_URL` — public HTTPS URL of hubx-gw (e.g., `https://hubx-gw.onrender.com`), set after first deploy

**Note on `sync: false`:**
These variables are not auto-synced because the Blueprint reference has no way to express public HTTPS service URLs. After the first deploy, Render will assign public URLs; copy them into `API_URL` and `GATEWAY_URL` manually, then trigger a redeployment.

### 5. First Deploy

1. Click "Deploy Blueprint" in the Render dashboard
2. Wait for all three services to build and start
3. Copy the public `.onrender.com` URLs assigned to `hubx-gw` and `hubx-api`
4. Update `API_URL` (gateway → api) and `GATEWAY_URL` (mfe → gateway) in the Render environment
5. Trigger a redeployment of hubx-gw and hubx-mfe

### 6. Verify Deployment

After services restart:

```bash
# Gateway health (public, no auth required)
curl -s https://<hubx-gw-url>.onrender.com/health | jq .

# API health through the gateway (public, no auth required)
curl -s https://<hubx-gw-url>.onrender.com/api/health | jq .
```

## Notes on Free Tier

- **Render free services** sleep after a period of no traffic and cold-start on the next request (expect a slow first response).
- **Neon free Postgres** suspends (scale-to-zero) after inactivity and resumes on the next connection; the first query after a suspend is slow.
- Because of these two, the very first request after idle can take tens of seconds. Retry if it times out.

## Smoke

2026-11-24, release v0.3.0. Run from a laptop against the public URLs.

| Check | Result |
|---|---|
| `GET https://hubx-gw.onrender.com/health` | 200 `{"service":"hubx-gw","status":"ok"}` |
| `GET https://hubx-gw.onrender.com/api/health` | 200 `{"status":"ok","service":"hubx-api"}` |
| `GET https://hubx-api.onrender.com/health` (direct, no gateway secret) | 401 `Request must come through the gateway` |
| `GET https://hubx-mfe.onrender.com/` | 200 (the app) |
| `POST https://hubx-mfe.onrender.com/api/auth/sign-in` as `operator@hubx.co` | 200 with a token and role `operator` |

## Staging (build once, deploy any commit)

Constitution 1.5.0: every push builds the images of its commit (`.github/workflows/images.yml` →
`ghcr.io/<owner>/hubx-{api,gw,mfe}:<sha>`). `.github/workflows/deploy.yml` deploys the images of **any** commit to an
environment: migrations → Render API (`imageUrl`) → wait for `live` → warm-up → Cucumber smoke. Staging receives every PR
merged into an integration branch (`deploy-staging.yml`, whatever the branch is called) and any ref on demand
(Actions → deploy → Run workflow → `staging` + branch, tag or SHA). The image tested in staging is the one promoted.

One-time setup (never paste a secret in a chat or the repo):

1. **Images public.** After the first `images` run on `main`, open each package (`hubx-api`, `hubx-gw`, `hubx-mfe`)
   under the repository's Packages → Package settings → Change visibility → Public (Render pulls without credentials).
2. **Neon.** Project `hubx` → Branches → New branch `staging` (from `main`). Copy its **direct** connection string.
3. **Render.** New → Blueprint → this repo, branch `main`, path `deploy/render.staging.yaml`. Values asked:
   `DB_URL` = the staging direct URL; `API_URL` = `https://hubx-api-stg.onrender.com`;
   `GATEWAY_URL` = `https://hubx-gw-stg.onrender.com` (fix them if Render assigns other URLs). Then Account settings →
   API keys → create one. Note each service ID (`srv-…`, in its URL or Settings).
4. **GitHub environment `staging`** (from your own terminal; `gh secret set` reads the value from stdin, hidden):
   ```bash
   gh api -X PUT repos/JairoHGomezCastillo/hubx/environments/staging >/dev/null
   gh secret set DB_URL --env staging          # paste the Neon staging direct URL, Enter
   gh secret set RENDER_API_KEY --env staging  # paste the Render API key, Enter
   gh variable set RENDER_SERVICE_API --env staging --body srv-...
   gh variable set RENDER_SERVICE_GW  --env staging --body srv-...
   gh variable set RENDER_SERVICE_MFE --env staging --body srv-...
   gh variable set GATEWAY_URL --env staging --body https://hubx-gw-stg.onrender.com
   gh variable set UI_URL      --env staging --body https://hubx-mfe-stg.onrender.com
   ```
5. **First deploy:** Actions → deploy → Run workflow → `staging`, ref `main`. Expected: migrations applied, three
   deploys `live`, warm-up, Cucumber green (all scenarios except `@needs-secret`).

### Clean database on every staging deployment

`deploy.yml` resets the Neon `staging` branch from its parent (production) before the migrations, so every staging
smoke starts from the same users and seed data (scenarios such as HU-07's "they see only their three shipments" need
it). The connection string does not change. One-time setup (your own terminal; the key is read from stdin, hidden):

```bash
gh secret set NEON_API_KEY --env staging          # Neon: Account settings -> API keys -> Create
gh variable set NEON_PROJECT_ID --env staging --body <project id>   # Neon: project Settings (also in its URL)
gh variable set NEON_BRANCH --env staging --body staging
gh variable set RESET_DB_FROM_PARENT --env staging --body true
```

Production never has `RESET_DB_FROM_PARENT`, and `scripts/deploy/neon-reset.sh` refuses a branch without a parent.
Data created by hand in staging is lost on the next deployment: create demo data after the last deploy.

## Production (image-backed, promoted by release.yml)

Every `release/*` or `hotfix/*` merged into `main` is tagged, then `release.yml` (job `deploy`) calls `deploy.yml` with
environment `production` and the **release tip**: the same commit and images that staging deployed and smoke-tested
(build once). Migrations run against the production database; the smoke runs only `@smoke` (health and sign-in, no
data written). The database is never reset (`RESET_DB_FROM_PARENT` exists only in `staging`). The job only runs when
the repository variable `DEPLOY_PRODUCTION` is `true`, which is also the switch to turn it off.

One-time setup (your own browser and terminal; never paste a secret in a chat or the repo):

1. **Render.** New → Blueprint → this repo, branch `main`, path `deploy/render.production.yaml`. Values asked:
   `DB_URL` = the Neon **production** (root branch) direct URL; `API_URL` = `https://hubx-api-prod.onrender.com`;
   `GATEWAY_URL` = `https://hubx-gw-prod.onrender.com` (fix them if Render assigns other URLs). Note each service ID.
2. **GitHub environment `production`:**
   ```bash
   gh api -X PUT repos/JairoHGomezCastillo/hubx/environments/production >/dev/null
   gh secret set DB_URL --env production          # paste the Neon production direct URL, Enter
   gh secret set RENDER_API_KEY --env production  # the Render API key, Enter
   gh variable set RENDER_SERVICE_API --env production --body srv-...
   gh variable set RENDER_SERVICE_GW  --env production --body srv-...
   gh variable set RENDER_SERVICE_MFE --env production --body srv-...
   gh variable set GATEWAY_URL --env production --body https://hubx-gw-prod.onrender.com
   gh variable set UI_URL      --env production --body https://hubx-mfe-prod.onrender.com
   ```
3. **First deploy:** Actions → deploy → Run workflow → `production`, ref = the latest tag (for example `v0.6.1`).
   Expected: migrations up to date, three deploys `live`, `@smoke` green.
4. **Switch on the promotion:** `gh variable set DEPLOY_PRODUCTION --body true`.
5. **Retire the repo-built services** (`hubx-api`, `hubx-gw`, `hubx-mfe`, Blueprint `deploy/render.yaml`): turn off
   their auto-deploy first, and delete them once the `-prod` URLs are the ones shared.

Agents never deploy to production: the devops guard denies `gh workflow run deploy.yml*production*`; only the release
merge (a human decision) or a human from Actions does.
