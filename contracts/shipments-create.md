# HTTP Contract: POST /api/shipments

**Story**: HU-02 Create a shipment
**Version**: 1.0
**Status**: Draft (pending implementation)

The MFE calls `POST /api/shipments` on the gateway; the gateway validates the JWT, strips `/api`, injects
`X-Gateway-Secret` and forwards `POST /shipments` to the API. The API validates the JWT again on its own
(constitution II) and authorizes by the `role` claim.

## Request

**Headers**:
```
Authorization: Bearer <token>
Content-Type: application/json
```

**Body** (maximum 16 KiB; larger bodies are rejected as `MISSING_REQUIRED_FIELDS`):
```json
{
  "origin": "Bogotá",
  "destination": "Miami",
  "flight": "AV-204",
  "weightKg": 120,
  "customerEmail": "andina@hubx.co"
}
```

| Field | Type | Rule |
|---|---|---|
| `origin` | string | required; trimmed; blank counts as missing |
| `destination` | string | required; trimmed; must differ from `origin` ignoring case and surrounding spaces |
| `flight` | string | required; trimmed; several shipments may share it |
| `weightKg` | JSON number | required; `0.1 <= weightKg <= 5000`; at most one decimal |
| `customerEmail` | string | required; normalized (trim, lower case) like sign-in; must belong to a user with role `customer` |

Unknown fields are ignored. The creating operator is the JWT `sub`; it is never taken from the body.

## Validation order

The first failing check answers; nothing is stored unless every check passes.

1. Session: missing, invalid or expired token -> `401` (bodies in `contracts/auth-sign-in.md`).
2. Role: `role != "operator"` -> `403 FORBIDDEN`. The body is not examined.
3. Body: malformed JSON, body over 16 KiB, or any required field missing/blank -> `400 MISSING_REQUIRED_FIELDS`.
4. Origin equals destination -> `400 SAME_ORIGIN_DESTINATION`.
5. Weight not a number, out of range or with more than one decimal -> `400 WEIGHT_OUT_OF_RANGE`.
6. No user with that email -> `422 CUSTOMER_NOT_FOUND`.
7. User exists but role is not `customer` -> `422 CUSTOMER_NOT_CUSTOMER_ROLE`.

## Responses

### 201 Created

```json
{
  "code": "HBX-7F3A9C21",
  "origin": "Bogotá",
  "destination": "Miami",
  "flight": "AV-204",
  "weightKg": 120,
  "customer": { "email": "andina@hubx.co", "name": "Distribuciones Andina" },
  "stage": "Created",
  "createdAt": "2026-11-24T15:04:05Z"
}
```

- `code`: `HBX-` followed by 8 upper-case hexadecimal characters, generated by the API from a cryptographically
  secure random source; unique (database constraint, regenerated on collision). Seed codes `HBX-SEED-NNNN` keep
  their own form.
- `stage`: always `Created`. No update is recorded (the shipment's chain is empty; the first update is `In flight`,
  HU-03).
- `createdAt`: RFC 3339, UTC.

### Errors

All error bodies have the shape `{"error": "<CODE>", "message": "<text>"}`.

| Status | `error` | `message` |
|---|---|---|
| 400 | `MISSING_REQUIRED_FIELDS` | `Required data is missing` |
| 400 | `SAME_ORIGIN_DESTINATION` | `The origin and the destination must be different` |
| 400 | `WEIGHT_OUT_OF_RANGE` | `The weight must be between 0.1 and 5000 kg` |
| 401 | `UNAUTHORIZED` | see `contracts/auth-sign-in.md` (missing, invalid, `Session expired. Please sign in again.`) |
| 403 | `FORBIDDEN` | `You do not have permission to create shipments` |
| 422 | `CUSTOMER_NOT_FOUND` | `The customer indicated does not exist` |
| 422 | `CUSTOMER_NOT_CUSTOMER_ROLE` | `The customer indicated does not have the customer role` |
| 500 | `INTERNAL_SERVER_ERROR` | `An unexpected error occurred` |

## Examples

```bash
TOKEN=$(curl -s -X POST http://localhost:8080/api/auth/sign-in \
  -H 'Content-Type: application/json' \
  -d '{"email":"operator@hubx.co","password":"Hubx-Demo-2026"}' | jq -r '.token')

curl -s -X POST http://localhost:8080/api/shipments \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"origin":"Bogotá","destination":"Miami","flight":"AV-204","weightKg":120,"customerEmail":"andina@hubx.co"}'
# 201, stage "Created"
```

## Security

- Parameterized queries only; the API inserts into `shipments` and never touches `updates` in this endpoint.
- Function-level authorization on the server (OWASP API5); the role comes from the validated JWT, never the body.
- Body size cap (OWASP API4); `created_by` from the JWT (OWASP API3: no mass assignment of `stage`, `code`,
  `created_by` or `assigned_partner_id`, which are ignored if sent).
