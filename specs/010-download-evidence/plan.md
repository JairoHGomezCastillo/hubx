# Implementation Plan: Download the traceability evidence

**Branch**: `010-download-evidence` | **Date**: 2026-11-25 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/010-download-evidence/spec.md`

## Summary

HU-10 adds a read-only, operator-only endpoint that assembles a shipment and its whole traceability chain into an
English PDF evidence document. The API reuses the existing visibility rule, ledger and party repositories, and
generates the PDF with a minimal stdlib writer so that no new Go dependency is introduced. The MFE exposes a
"Download evidence" page reachable from the Dashboard; the browser saves the PDF via a blob URL. QA automates all
backlog scenarios against the API through the gateway plus one `@e2e` download happy path in Chromium. No migration,
no new business event and no gateway change are needed.

## Technical Context

**Language/Version**: Go 1.27.4 (stdlib `net/http`, `ServeMux`); TypeScript strict + React 19 + Vite; Node 24 in CI.

**Primary Dependencies**: existing ones only — `pgx/v5` (PostgreSQL), `golang-jwt/jwt/v5`, `golang.org/x/crypto`
(bcrypt), `go.uber.org/mock` (tests); React/React-DOM, Cucumber 13.3.0, Playwright 1.65.0, tsx. **No new dependency**:
the PDF is written with the Go standard library.

**Storage**: PostgreSQL, accessed only by hubx-api. Reuses the `shipments`, `updates` and `users` tables from
migration 0001; no new table, no migration, no write to the ledger.

**Testing**: `go -C hubx-api test ./...`, `go -C hubx-gw test ./...`, `npm --prefix hubx-mfe run test`,
`make test-integration` (Cucumber API + `@e2e`), `make security` (`gosec`, `govulncheck`).

**Target Platform**: Linux containers (distroless Go services, nginx-served MFE) and local Docker Compose.

**Project Type**: web service + single-page application + BDD QA workspace.

**Performance Goals**: a small document (a handful of updates) downloads in one request; no streaming or pagination
required. No new latency target beyond the existing stack.

**Constraints**: Constitution III forbids new Go dependencies without human approval; Constitution I requires all
ledger access through `LedgerRepository`; Constitution II requires JWT validation in the API and all MFE traffic via
the gateway; Constitution VI requires parameterized queries and a privacy-preserving answer for invisible shipments.

**Scale/Scope**: one endpoint, one MFE page, one feature file; 6 backlog scenarios (one Scenario Outline with two
roles) and one `@e2e` happy path.

**Structure Decision**: the new domain follows the Go layout already used by HU-04/HU-05 (domain, handler, `test/`,
`mocks/`). Visibility stays in the `shipment` package and is exported once so the reader, traceability reader,
verifier and recorder all share one rule. PDF bytes are produced in the API, not the MFE, so the document is complete
and self-contained before it reaches the browser.

## Complexity Tracking

| Item | Why Needed | Simpler Alternative Rejected Because |
|---|---|---|
| Minimal stdlib PDF writer | FR-011 requires PDF and Constitution III forbids new Go dependencies without human approval. | A PDF library would need a human-approved dependency (not granted for this story); browser print would not deliver a downloadable PDF from the API and would not be usable by a third party without HUBX. |
| Export `shipment.CanSee` | HU-10, HU-04 and HU-05 must apply the identical visibility rule; duplicating it risks divergence. | A private copy in the new package would duplicate business logic and break Constitution VI's privacy rule if it drifted. |
| Extend `ShipmentRepository.FindByCode` projection | FR-012 requires origin, destination, flight, weight and customer name, which the current query does not read. | Populating them only at creation would be impossible for shipments loaded from the database in a later session. |
